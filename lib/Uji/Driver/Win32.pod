=head1 NAME

Uji::Driver::Win32 - the Windows backend (FFI to user32/gdi32/comctl32)

=head1 SYNOPSIS

    my $driver = Uji::Driver::detect();    # Uji::Driver::Win32 on MSWin32

    Uji::app(
        init   => \&init,
        update => \&update,
        view   => \&view,
        driver => $driver
    )->run;

=head1 DESCRIPTION

L<Uji::Driver::Win32> implements L<Uji::Driver|Uji::Driver> on Windows using FFI (L<Affix>) straight into
C<user32.dll>, C<gdi32.dll>, and C<comctl32.dll>. No XS, no CPAN module wrapping the Win32 API: the driver creates a
window class, pumps messages, mounts controls (BUTTON, STATIC, EDIT, TRACKBAR), routes C<WM_COMMAND>/C<WM_HSCROLL>
notifications, and applies reconciler updates - all through raw Win32 calls.

=head1 Constructor

=head2 C<new (%opts)>

Constructed by C<Uji::Driver::detect()> with no options; an explicit driver can pass:

=over 4

=item C<dark_mode =E<gt> 0|1>

Pin the colour scheme: C<1> forces dark, C<0> forces light. The default (C<undef>) probes the OS
theme (C<HKCU\...\Themes\Personalize\AppsUseLightTheme>) in C<uses_dark_mode>. Pinning skips the
registry read -- useful for demos (C<eg/widget_dark_mode.pl>) and tests.

=item C<dpi =E<gt> $n>

Explicit DPI override (tests use C<144>); the default probes the display DPI.

=back

Internally the constructor registers the FFI affixes and calls C<InitCommonControlsEx> so common
controls (trackbars) are available.

=head1 Methods

=head2 C<init ( $channel )>

Registers the C<'UjiWindowClass'> window class and its window procedure, and stores the message channel the C<on_*>
handlers write to.

=head2 C<mount ( $vtree )>

Creates the top-level window with C<CreateWindowExW>. Style is C<WS_OVERLAPPEDWINDOW> minus C<WS_THICKFRAME> when the
window is C<resizable =E<gt> 0>. Honor C<centered>, C<topmost>, C<minimized>/C<maximized>, then measures the real
client size back into the window node's bounds.

=head2 C<mount_children ( $vtree )>

Recursively creates child controls for the tree (see L<Uji::Node|Uji::Node> types): BUTTON
(text/button/checkbox/radio), STATIC (text labels and C<SS_ETCHED*>-styled separators), EDIT (text/multi-line/password,
with C<ES_PASSWORD> or the multi-line style bits), and C<msctls_trackbar32> sliders. Every control is created at its
computed absolute bounds; initial state (enabled, visible, tooltip, checked, slider range) is applied immediately.
Containers get no native handle, but a C<radio_group> gets a registry entry so C<set_prop('value')> can route check
state to its radio children.

=head2 C<poll_events ()>

A non-blocking drain of the message queue via C<PeekMessageW>, C<TranslateMessage>, C<DispatchMessageW>. Blocking
messages are filtered out so the fiber can yield.

=head2 C<set_prop ( $node_id, $prop_name, $value )>

See L<Uji::Driver|Uji::Driver/set_prop>. Implemented property branches and their native calls:

=over

=item * C<title> - C<SetWindowTextW> on the main window.

=item * C<topmost> - C<SetWindowPos> with C<HWND_TOPMOST>/C<HWND_NOTOPMOST>.

=item * C<minimized> / C<maximized> - C<ShowWindow> C<SW_MINIMIZE>/C<SW_MAXIMIZE>/C<SW_RESTORE>.

=item * C<min_w>/C<min_h>/C<max_w>/C<max_h> - re-clamps the live window size via C<WM_GETMINMAXINFO>-style math.

=item * C<label> - C<SetWindowTextW> + C<InvalidateRect>.

=item * C<value> - slider via C<TBM_SETPOS>; spin box via C<UDM_SETPOS32> (the edit text follows, since
the driver owns it); progress bar via C<PBM_SETPOS>; radios via C<BM_SETCHECK> routed from the group's C<value>; edits via
C<SetWindowTextW> (skipped when the native text already matches, so the caret never jumps).

=item * C<enabled> - C<EnableWindow>.  C<visible> - C<ShowWindow> (C<SW_SHOW>/C<SW_HIDE>).
The spin box's up/down buddy follows both.

=item * C<focused> - C<SetFocus> when true.

=item * C<tooltip> - attaches/replaces a tooltip via a shared C<TOOLTIPS_CLASS32> control.

=item * C<readonly> - C<EM_SETREADONLY>.  C<maxlength> - C<EM_LIMITTEXT>.

=item * C<step> - C<TBM_SETLINESIZE>/C<TBM_SETPAGESIZE>; spin box via C<UDM_SETACCEL>.  C<checked> -
C<BM_SETCHECK> (checkboxes and both toggle widgets).

=item * C<min>/C<max> - C<TBM_SETRANGE>, C<PBM_SETRANGE32>, or C<UDM_SETRANGE32> per control type.

=item * C<placeholder> - C<EM_SETCUEBANNER> (text inputs, multi-line, password).

=item * C<password_char> - C<EM_SETPASSWORDCHAR> + repaint (password).

=item * C<color> / C<background> - cached on the registry record; the OS asks for them on the next paint via the
C<WM_CTLCOLOR*> notifications (below). A C<InvalidateRect> forces the repaint immediately.

=item * C<font> / C<font_size> - builds (or reuses) a matching font via C<CreateFontIndirectW> + C<WM_SETFONT>, cached on
the registry record.

=back

=head2 C<recreate_node ( $node_id, $vnode )>

Destroys the native control behind C<$node_id> and recreates it from scratch with C<$vnode>'s current properties. Used
when a mount-only property changed - C<multiline> (edits), C<orientation> (sliders), C<align> (text) - because those
are baked into the window style at creation time and cannot be changed in place. The tree's C<id> is preserved so the
registry and every event binding keep working; style-affecting parameters (label, color, background, font) are
re-applied immediately after recreation.

=head2 C<move_widget ( $node_id, $x, $y, $w, $h )>

C<SetWindowPos> to an absolute box; skipped for container nodes (no native handle).

=head2 C<measure_text ( $text )>

Measures a string with the standard GUI font (C<GetTextExtentPoint32W>) so layout intrinsic sizes match the real
controls.

=head2 C<sync_window_bounds ( $vtree )>

Reads the window's client size via C<GetClientRect> and writes it back to the window node's bounds.

=head2 C<_theme_control ( $hwnd )>

In a dark scheme, applies the C<DarkMode_Explorer> uxtheme to a window/control so comctl surfaces
(scrollbars, combobox popups, trackbars, tabs, tooltips) and the C<BUTTON>/C<EDIT> classes render dark;
no-op in light mode. On builds where the uxtheme hook-up silently no-ops (the dark "Explorer" theme lacks
dark button/checkbox/radio parts), the C<BUTTON>/C<EDIT> controls fall through to the C<WM_CTLCOLOR*>
recolouring instead, so both paths coexist. STATIC text is deliberately left unthemed - its fill already
comes from the CTLCOLOR brush.

=head2 C<_enable_dark_theme ()>

Best-effort hook-up of Windows' undocumented dark-mode helpers. uxtheme exports them by ordinal only:
C<135> (C<SetPreferredAppMode>, C<AllowDarkModeForApp> on 1809), C<133> (C<AllowDarkModeForWindow>),
C<136> (C<FlushMenuThemes>). Resolved at runtime via C<GetProcAddress> and skipped when absent, so the
driver also runs on builds without them; nothing is called unless C<uses_dark_mode> is true.
C<AllowDarkModeForWindow> is applied during the top window's C<WM_NCCREATE> (it is ignored after
creation).

=begin comment

Owner-drawn dark checks: B<the offline paint test chain does NOT work> here. An owner-drawn
BUTTON paints when the button's WndProc receives C<WM_PAINT>, which only happens inside a live
ShowWindow/UpdateWindow pump; an I<offline> C<InvalidateRect>+C<UpdateWindow> chain posts nothing.
To force one render from a test, send C<WM_PAINT> (0x000F) synchronously to the control with
C<SendMessageW>; the button replies by sending C<WM_DRAWITEM> to its parent, whose wndproc is the
driver's C<_ctrl_msg>. See C<t/037_owner_draw_check.t>.

=end comment

=head2 Owner-drawn dark checks, radios and toggles

The Win32 classic/theme renderer has no dark parts for C<BUTTON> checks, radios or push-like
toggle buttons, so in a dark scheme the driver mounts these controls with C<BS_OWNERDRAW> (0xB)
and paints them from the dark palette through C<WM_DRAWITEM> in C<_draw_check_button> (square box /
radio circle, accent check mark / dot, and a light label). In light mode the native sub-types are
kept (BS_AUTOCHECKBOX = 3, BS_AUTORADIOBUTTON = 9) and the system renders them.

Two consequences of C<BS_OWNERDRAW> to be aware of:

=over

=item *

There is I<no native check state>. C<BS_OWNERDRAW> replaces the auto-check sub-type, so
C<BM_GETCHECK>/C<BM_SETCHECK> are inert and C<BM_CLICK> does not toggle anything natively. The
driver mirrors the check/selection in the registry record: the C<check> key is written at mount
from C<checked> (checkbox/toggle) or C<selected> (radio), flipped on the C<BN_CLICKED> that
C<BM_CLICK> - and real clicks - still generate, and written by C<set_prop('checked')> and the
C<radio_group> C<value> branch. C<_draw_check_button> reads that flag first and only falls back to
C<BM_GETCHECK> for legacy light paths. Radio siblings synchronise through the registry via
C<_radio_group_for> + C<_apply_radio_group>, since WS_GROUP auto-radio behaviour does not exist for
the owner-drawn type.

=item *

C<WM_DRAWITEM> is delivered to the control's I<parent> window (the app window), not to the control.
The parent's wndproc is the driver's C<_ctrl_msg>, which resolves the control by C<hwndItem> and
dispatches to the draw handler. The C<DRAWITEMSTRUCT.hwndItem> field is typed C<Size_t>
(not an opaque pointer) so the HWND value survives the Affix round-trip.

=back

=head1 How it Works

=head3 The Window Procedure

C<init> installs a single window procedure that translates native notifications into the toolkit's message channel:

=over

=item C<WM_COMMAND> (C<0x0111>) - the big one. C<BN_CLICKED> notifications route to C<on_click> (button):
a static hashref is sent verbatim, a callback is invoked and its return value sent. For checkboxes the
current check state is read back with C<BM_GETCHECK> before calling C<on_toggle>. Radio clicks dispatch
C<on_select> with the clicked option's value. C<EN_CHANGE> calls C<on_input> with the control's current
text. C<CBN_EDITCHANGE> does the same for editable combo boxes, and C<CBN_SELCHANGE>/C<LBN_SELCHANGE>
call C<on_select> with the picked option's value - or, for a multi-select list (C<multiple>), with an
arrayref of the selected option values. Two C<BN_CLICKED> special cases are routed through command-id
tables instead of the control registry: toolbar buttons (C<toolbar_cmds>, ids 0x4000+) and menu-bar
items (C<menu_cmds>, same allocator) both dispatch C<on_click> with the item's C<id>.

=item C<WM_HSCROLL> (C<0x0114>) - slider drags read C<TBM_GETPOS> and call C<on_change>.

=item C<WM_VSCROLL> (C<0x0115>) - two cases. A vertical slider reports its own handle as C<lParam>: the registry lookup
succeeds, the position is read with C<TBM_GETPOS>, and C<on_change> fires. A spin box's C<msctls_updown32> buddy is
instead reachable as the C<aux> entry of its registry record; its position is read with C<UDM_GETPOS32>, the edit text
is re-synced by the driver, and C<on_change> fires with the new value.

=item C<WM_CTLCOLORSTATIC> (C<0x0138>), C<WM_CTLCOLOREDIT> (C<0x0133>), C<WM_CTLCOLORBTN> (C<0x0135>) - the control's
C<lParam> resolves through the registry; when a C<color>/C<background> is set, the driver calls C<SetTextColor>
(C<color>) and/or C<SetBkColor> + selects a cached brush (C<background>) onto the C<wParam> DC. Never passes through
C<DefWindowProcW>, which would reset the DC colours the OS already chose; instead it returns a system brush
(C<COLOR_WINDOW> for edits, C<COLOR_BTNFACE> for statics/buttons) as the default. The return value is the brush
I<handle>: the driver returns C<Affix::address($brush)> (an Affix object would numify to its Perl SV address, an
invalid GDI handle that Windows silently rejects and paints white). Note the DC state is restored by Windows after
the notification, so the colours only show up on the real paint, not on a direct C<SendMessageW>+C<GetTextColor>
read-back. Limitation: checkboxes/radios in the classic renderer ignore the returned brush/label colour and paint
their own white box + black label; on builds where the C<DarkMode_Explorer> uxtheme binds (see C<_theme_control>)
they go dark natively instead. Push buttons are never dark in the Win32 classic/theme renderers.

=item C<WM_SIZE> - puts a reserved C<RESIZE> message and triggers a synchronous re-layout (so live resizing never
shows stale layout).

=item C<WM_GETMINMAXINFO> - clamps the track size to C<min_w>/C<min_h>/C<max_w>/C<max_h>.

=item C<WM_DESTROY> - puts C<< { type => 'QUIT' } >> so the process exits with the window.

=back

All produced messages are plain hashrefs C<put> onto the channel for L<Uji::App|Uji::App/How it Works> to fold through
C<update>.

=head3 The Registry

Every mounted control - and the window itself - is recorded in an id-keyed registry mapping C<id E<rarr> { hwnd, node
}>. C<WM_GETMINMAXINFO>, C<WM_HSCROLL>, C<WM_VSCROLL>, the C<WM_CTLCOLOR*> notifications, and C<set_prop> all resolve
the native handle the same way the reconciler indexes nodes: by id. Containers and C<radio_group> carry C<hwnd =>
undef> entries (the group only routes state to its radio children). The spin box's up/down buddy is reachable as the
C<aux> entry of its registry record; the current C<color>/C<background>/C<font>/C<font_size> caches and the readonly
flag are also kept per record so a recreation or repaint can re-apply them.

=head3 Win32 Control Mapping

=over

=item C<text_input> / C<multiline_text> / C<password> - a C<STATIC>/C<EDIT> family. Text inputs are single-line
C<EDIT> controls (C<WS_CHILD | WS_VISIBLE | WS_BORDER | ES_AUTOHSCROLL>). With C<multiline> set the style becomes
C<WS_CHILD | WS_VISIBLE | WS_BORDER | WS_VSCROLL | WS_TABSTOP | ES_MULTILINE | ES_AUTOVSCROLL>; the
L<Uji::Node::MultilineText|Uji::Node::MultilineText> subclass is created with exactly that style and never changes it.
Password fields add C<ES_PASSWORD>. C<WS_TABSTOP> on multi-line lets Tab move focus instead of inserting a tab;
C<ES_AUTOVSCROLL> keeps the caret visible as the text grows. C<placeholder> paints grey hint text with the driver's
paint handler while the native text is empty; C<password_char> maps to C<EM_SETPASSWORDCHAR>.

=item C<spin_box> - a read-only C<EDIT> and its C<msctls_updown32> buddy placed SIDE BY SIDE (edit
width = C<bw - SM_CXVSCROLL>, buddy owns the right strip), the classic Win32 spin layout. An earlier
overlay scheme put the edit under the buddy in the parent's z-order, so the edit swallowed arrow
clicks (value never changed, caret sat "in front" on Windows). The driver owns the edit text, because
the classic C<UDS_SETBUDDYINT> lazy C<WM_SETTEXT> into a read-only edit is a re-entrancy/crash trap.
Arrow clicks surface as C<WM_VSCROLL> from the buddy. Requires C<ICC_UPDOWN_CLASS>.

=item C<search_input> - a single-line C<EDIT> (C<WS_CHILD | WS_VISIBLE | WS_BORDER | ES_AUTOHSCROLL>) with
two SIBLING auxiliaries: an optional leading icon glyph (C<STATIC> + C<SS_ICON|SS_CENTERIMAGE>, fed by the
same GDI+ raster loader the toolbar uses) and a trailing flat "clear field" button (C<✕>). The edit's
C<EM_SETMARGINS> reserve those strips so text and caret never run under them. Keystrokes surface as
C<EN_CHANGE> -> C<on_input>; clicking C<✕> empties the field, refocuses it, and fires C<on_search('')>.
The clear button takes a fresh C<0x4000+>-range command id from the driver-wide allocator and carries a
registry record (C<search_clear> => 1) so its C<BN_CLICKED> routes to the owning node. C<icon> is a
mount-only property (changing it recreates the control; the orphaned glyph C<STATIC> is destroyed and the
stale command id is dropped from the routing table). Enter-key submission is not wired (no control
subclassing); pair the field with a "Search" button in the model.

=item C<calendar> - a COMPOSED widget: no native class is created. The node expands into ordinary
controls (a header of C<◀>/C<▶> buttons and a title C<STATIC>, a weekday C<STATIC> row, and six
rows of 28x22 day C<BUTTON>s), mounted under the same containers as any other tree. Because the cell
ids are regenerated every render, the cell ids are numeric: the driver allocates a C<0x6000+>-range
control id for any node whose id is a string (reverse map C<cid_to_id>), keeping C<WM_COMMAND> routing
working, and the reconciler re-mounts the whole cell tree when the grid changes.

=item C<overlay> - a COMPOSED container: layers mount as plain WS_CHILD siblings of the host window
(no control of its own, like C<column>/C<row>). Native creation order would put the FIRST sibling on
top, but an overlay's array order is its draw order, so B<C<_apply_overlay>> re-raises each layer with
C<HWND_TOP> in array order after mounting and after every reconcile - the LAST layer ends up
frontmost. C<_raise_layer> recurses through container layers (no HWND of their own) to raise every
sub-control.

=item C<date_picker> - C<SysDateTimePick32> with the C<DTS_SHORTDATEFORMAT>/C<DTS_LONGDATEFORMAT>/
C<DTS_TIMEFORMAT>, C<DTS_SHOWNONE> and C<DTS_UPDOWN> style bits derived from C<format>/C<show_none>/
C<useynavigate>. Mount and live changes write the ISO value with C<DTM_SETSYSTEMTIME> (C<GDT_NONE> when
the value is empty) and the natural range with C<DTM_SETRANGE>; user edits surface via
C<DTN_DATETIMECHANGE>, read back through C<DTM_GETSYSTEMTIME>, and are completed to C<'YYYY-MM-DD'>.
Requires C<ICC_DATE_CLASSES>.

The buddy's own hot-track/click repaints can erase its arrow glyphs under the poll-based pump (seen on dark-mode +
Strawberry). Two driver-side guards keep the arrows rendered: a deterministic C<InvalidateRect>+C<UpdateWindow> right
after mount, and C<_repaint_active_spin_arrows> (called from C<poll_events> every tick) which repaints any spin buddy
the cursor is currently over (plus one repaint on the cursor-exit transition).

=item C<progress_bar> - C<msctls_progress32>, plain determinate (smooth), range/position via
C<PBM_SETRANGE32>/C<PBM_SETPOS>. Requires C<ICC_PROGRESS_CLASS>.

=item C<spinner> - an animated activity indicator with NO native "busy" control: comctl32's
C<PBM_SETMARQUEE> needs the comctl32 v6 manifest this app avoids, so the driver draws its own. It
pre-renders 12 HICON frames of a GDI+ C<GdipDrawLineI> spoke fan (a bright head watching dimming
towards the tail; the anti-aliased pen comes from C<GdipCreatePen1> - note the pen must be passed to
draw calls as the RAW pointer value, not the malloc'd Affix I<object>) and hosts it on a STATIC
C<SS_ICON | SS_CENTERIMAGE> child. Each spinner arms a WM_TIMER (id = its control id, so the shared
C<_ctrl_msg> WM_TIMER branch looks it up in the registry and advances the I<frame>/C<STM_SETICON>
cycle; the same message number the app wndproc already uses for its drag-modal pump at id 1);
setting C<running> =E<gt> 0> disarms it via the C<set_prop('running')> path. This is why the C<GdipDrawArc>
flat API is NOT affixed: its six C<Float> args mis-marshal under the current Affix and crash the
caller, hence integer C<GdipDrawLineI> only.

=item C<image> - a STATIC C<SS_BITMAP> picture holder. The shared GDI+ loader decodes a file path or
C<data:image/...;base64,..> URI and rasters it into the widget's EXACT box (reuse of C<_raster_hbitmap>,
cached per src@w@h@fit), then C<STM_SETIMAGE> with wParam = C<IMAGE_BITMAP> (0). C<object_fit>
maps to C<contain> (centred letterbox), C<cover> (centre crop) or C<fill> (stretch); transparent
pixels composite onto the dialog-face colour because a GDI STATIC draws the bitmap opaquely. The GIANT
pain: the picture is re-rastered on every C<move_widget> that changes w x h (the layout fixes the box
after mount), so the mount default 16x16 never survives to screen.

=item C<canvas> - a dedicated C<UjiCanvasClassN> child (a per-instance window class whose proc handles
WM_PAINT + WM_ERASEBKGND) that draws the node's C<on_draw> into a GDI+ back-buffer the exact size of
the client rect: create a bitmap (C<PixelFormat32bppPARGB>), clear it to C<background>, run the callback
through L<Uji::Draw> (the GDI+ implementation L<Uji::Draw::Win32>), composite to an HBITMAP and BitBlt
it SRCCOPY. WM_ERASEBKGND returns 1 so nothing
else paints (no flicker, no background flash); the control is invalidated at mount, on resize, when the
reconciler sets C<on_draw>/C<redraw>, and by C<move_widget> when its box changes. The paint reads the
CURRENT node (the registry is kept fresh), so a reconciled callback or background is picked up on the
next repaint with no cached state to sync.

=item C<toggle_switch> / C<toggle_button> - a C<BUTTON> with C<BS_AUTOCHECKBOX | BS_PUSHLIKE>
(C<0x50001003>): auto-toggles itself on click and reads back via C<BM_GETCHECK>, exactly like a checkbox
but rendered as a sticky pushed button.

=item C<link_button> - a C<BUTTON> with C<BS_FLAT> (C<0x50008000>): an edge-less click target that posts
the same C<BN_CLICKED> notification as a plain button. (A true C<SysLink> would require the comctl32 v6
manifest; BS_FLAT keeps the app manifest-free.)

=item C<toolbar> - C<ToolbarWindow32>. Labels go into the native string table with C<TB_ADDSTRINGW>, which
requires C<wParam = 0> and a double-null-terminated UTF-16 buffer (passing a count or a single terminator
makes it return -1 and the button stays blank). Per-button C<icon> specs are decoded to HICONs through the
GDI+ flat API (gdiplus.dll - note the export is C<GdipLoadImageFromFile>, not C<...W>) and collected into a
per-toolbar C<ImageList> (ILC_COLOR32) attached with C<TB_SETIMAGELIST>. Gotcha: the driver's C<SendMessageW>
declares C<lParam> as C<SSize_t>, so a boxed Affix pointer REF must be unwrapped with C<Affix::address>
before use - passing the REF itself marshals the SV's own address (the same quirk applies anywhere a pointer
is written into a struct field).

=back
